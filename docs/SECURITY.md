# Security

The repository is **public** and the platform runs code, deploys servers and takes payments on behalf of its users. These rules apply to every change. To report a vulnerability, see [SECURITY.md](../SECURITY.md) at the repository root.

## Secrets

- No secret in the repository, in a document, in a test fixture or in a front-end bundle. The pre-commit hook blocks the common cases; CI runs gitleaks on every push.
- Production secrets live in Google Secret Manager, one entry per application: see [Configuration and secrets](CONFIGURATION.md).
- A secret that was ever committed or shipped in a bundle is compromised: rotate it, then clean the history. Deleting it in a later commit is not enough.

## Identity and sessions

- Identity comes only from a verified credential: the Firebase ID token at sign-in, then the API's `session` cookie. Never trust a user id, e-mail or role sent in a request body or header.
- Session and refresh cookies are `httpOnly`, `Secure` in production, `SameSite=Lax`, scoped to `.idem.africa`. Tokens are never returned in response bodies.
- Refresh tokens are stored hashed. Signing out revokes the refresh token.
- Administrator rights (`ADMIN_EMAILS`) require a Firebase-verified e-mail address. Internal routes (`/billing/internal/*`) require `INTERNAL_API_KEY`, compared in constant time.
- OAuth flows sign their `state` and must finish in the session that started them.

## Authorization

- Every read or write of user data is scoped to the authenticated user (API: `users/<uid>/projects`; iDeploy: `team_id`). A missing scope is a cross-tenant leak.
- Clients cannot write ownership or system fields (`userId`, `deployments`, `policyAcceptance`…): the API strips them from project updates.
- In iDeploy, running arbitrary commands (exec, scheduled tasks, a terminal on a server host) is reserved to team owners and admins.

## Untrusted input

- **Shell commands** (iDeploy, deployments): every user value is validated, then passed with single-quote escaping (`shellQuote`). Never build a command with double quotes, `JSON.stringify` or raw interpolation. Git branches and repository URLs go through `validation/git-input.ts`.
- **Docker Compose from users** is checked by `docker/compose-policy.ts` before it runs: no privileged mode, host namespaces, host bind mounts, Docker socket or dangerous capabilities.
- **Files**: never read or write a path taken from a request. Uploads are size-limited.
- **Outbound requests to user-supplied URLs** go through `fetchPublicUrl` / `assertPublicUrl` (API): public addresses only, redirects re-checked.
- **HTML generated by models or edited by users**: rendered server-side only in Chromium with the render network guard (no internal network, no `file://`); shown in the dashboard only inside `sandbox="allow-scripts"` iframes.
- **LLM calls**: the client never chooses the provider, model, token limits or files. Only messages are accepted.

## Billing

Credit checks happen on the server, before generation, and fail closed: if billing cannot be checked in `enforce` mode, the request is refused. Payment callbacks are only trusted after the status is re-read from pawaPay.

## Errors, logs and limits

- 5xx responses in production do not expose internal messages; details stay in the logs.
- Never log tokens, cookies, request bodies of authentication routes or secret values.
- Rate limits are applied globally and per sensitive route (Redis, atomic).
- Swagger is disabled in production; `/metrics` can require `METRICS_TOKEN`.

## Dependencies

- Lockfiles are committed and pinned; `scripts/clean.sh` keeps them.
- CI fails on critical `npm audit` findings (production dependencies).
- GitHub Actions are pinned to commit SHAs.
