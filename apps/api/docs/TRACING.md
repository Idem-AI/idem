# Real-time tracing — watching what the AI does

> Built on the existing logging system (Winston). No new infrastructure: a dedicated log file + automatic correlation.

## 1. What exists

### Automatic correlation (`requestId`)

Every HTTP request gets a unique identifier (`requestId`), generated by [request-trace.middleware.ts](../api/middleware/request-trace.middleware.ts) and propagated through `AsyncLocalStorage` (the same mechanism as the language and the revision context). The logger ([config/logger.ts](../api/config/logger.ts)) injects it **automatically into EVERY log line** — `requestId`, `userId` (once authenticated) and `projectId` (as soon as a route/tool/service knows it) — without touching the ~200 `logger.info/warn/error(...)` calls already in the codebase.

The id is also returned in the `X-Request-Id` response header.

### Console output (`npm run dev` terminal)

The console format shows metadata **inline** for tracing events — the most direct way to follow in real time in the terminal running the API:

```
23:01:22 info: ai.agentic_turn · req=bb5282b4 turn=2 decision=tool_calls tools=[{"name":"project_finance_summary"}] userId=user123 projectId=proj456
23:01:22 info: ai.tool_call_end · req=bb5282b4 tool=project_finance_summary durationMs=42 ok=true …
23:01:22 info: chronicle.commit · req=bb5282b4 section=businessPlan version=3 authorType=user …
```

Classic text logs (which already carry everything in their message) are shown as they are. Only `logAIEvent` events (with an `event` field) get the `· key=value …` suffix.

### A dedicated file: `logs/ai-trace.log`

In addition to the existing files (`combined.log`, `error.log`), a file isolates only the AI/Chronicle/Coherence/HTTP tracing events (recognised by their namespaced `event` field):

```
tail -f apps/api/logs/ai-trace.log | jq .
```

Each line is a JSON object with at least: `timestamp`, `level`, `message` (= the event name), `event`, `requestId`, `userId`, `projectId` (when known), and the event's specific fields.

## 2. Traced events

| Event | Where | What it shows |
|---|---|---|
| `http.request_start` / `http.request_end` | every request | method, route, status code, duration |
| `ai.agentic_loop_start` / `ai.agentic_loop_end` | `PromptService.runPromptWithTools` | model, number of turns used, total duration |
| `ai.agentic_turn` | each turn of the loop | did the AI call tools or give its final answer? with which arguments? |
| `ai.tool_call_start` / `ai.tool_call_end` | each tool call (`project_*`) | which tool, with which arguments, result (preview), success/error, duration |
| `chronicle.commit` | each recorded revision | project, section, version, author (user/ai/system), changed paths |
| `chronicle.query` | `log` / `show` / `diff` / `stateAt` | what the AI (or the dashboard) looked for in the history |
| `coherence.scheduled` | after a project write | which coherence rule will be audited, and when |
| `coherence.verdict` | end of the AI audit | coherent or not, number of inconsistencies, recommended autofill |
| `coherence.alert_created` | an alert is created | rule, number of inconsistencies, autofill proposal |
| `advisor.message_received` / `advisor.finance_intent` / `advisor.tool_loop_fallback` / `advisor.reply_ready` | each advisor message | detected intent, possible fallback, length/duration of the reply |

Agent and quality events (`agent.*`, `quality.*`) are listed in [Agent architecture](AGENT_ARCHITECTURE.md#following-what-happens).

## 3. Example: following a question end to end

For the question "what is my revenue model?" you will see in `ai-trace.log` (same `requestId`):

```
http.request_start        { method: POST, path: /project/advisor/:id/messages }
advisor.message_received  { messageLength: 32 }
advisor.finance_intent    { isFinanceIntent: false, kind: "none" }
ai.agentic_loop_start     { modelName: "glm-4.7", toolCount: 9 }
ai.agentic_turn           { turn: 1, decision: "tool_calls", tools: [{name:"project_get_map"}] }
ai.tool_call_start        { tool: "project_get_map" }
ai.tool_call_end          { tool: "project_get_map", durationMs: 42, ok: true }
ai.agentic_turn           { turn: 2, decision: "tool_calls", tools: [{name:"project_finance_summary"},{name:"project_get_section", args:{section:"businessPlan"}}] }
ai.tool_call_start        { tool: "project_finance_summary" }
ai.tool_call_end          { tool: "project_finance_summary", ok: true }
ai.tool_call_start        { tool: "project_get_section" }
ai.tool_call_end          { tool: "project_get_section", ok: true }
ai.agentic_turn           { turn: 3, decision: "final_answer", finalTextLength: 480 }
ai.agentic_loop_end       { turnsUsed: 3, durationMs: 4210 }
advisor.reply_ready       { replyLength: 480, durationMs: 4530 }
http.request_end          { statusCode: 200, durationMs: 4550 }
```

Filter on one `requestId`:

```bash
grep '"requestId":"<id>"' apps/api/logs/ai-trace.log | jq .
```

## 4. Tracing a new feature

Call the existing helper — no new transport or configuration needed:

```ts
import { logAIEvent, previewValue } from '../../utils/ai-trace.util';

logAIEvent('branding.generation_start', { projectId, style });
// ...
logAIEvent('branding.generation_end', { projectId, durationMs, resultPreview: previewValue(result) });
```

The event name must start with one of the prefixes recognised by the filter (`http.`, `ai.`, `chronicle.`, `coherence.`, `advisor.`) to appear in `ai-trace.log` — otherwise add the prefix to `AI_TRACE_PREFIXES` ([config/logger.ts](../api/config/logger.ts)). `requestId`/`userId`/`projectId` are injected automatically; do not pass them.

To attach the `projectId` from the start of a service, call `setTraceProjectId(projectId)` (`utils/trace.util.ts`) once it is known — every later log of the request will carry it.

Never log tokens, cookies or secret values in an event: `previewValue()` truncates, it does not redact.

## 5. Verbosity

- `LOG_LEVEL` (env) sets the global level (default `info`) — all tracing events are at `info`.
- Files rotate automatically (5 files of 10 MB for `ai-trace.log`, like the other logs).

## 6. Pitfall: writable log files

Winston opens the files in `logs/` for writing at start-up. If a file belongs to another user (typically a Docker run **as root** leaving `combined.log`/`error.log` owned by `root`), the dev process started as a normal user **can no longer write** to it — the failure is silent (`exitOnError: false`) and the file stays frozen. Symptom: the file no longer changes while the API runs.

Fix: make the files writable by the user running the API (`sudo chown "$USER" logs/*.log`), or rename them so Winston recreates them at the next start (`mv logs/combined.log logs/combined.log.bak`). Check with `ls -la logs/` that the active files belong to the current user.
